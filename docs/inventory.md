# Блок `inventory`

Склад: скільки деталей лежить, де, скільки з них уже обіцяно нарядам і скільки
вони коштували. Перший блок Фази 2. Сам нічого не продає: деталі приходять з
прайсу (`catalog`), резерви й списання — подіями від `work-orders`.

## Чотири артефакти блоку

| Артефакт | Де лежить | Що це |
|---|---|---|
| Контракт | [`contracts/inventory.yaml`](../contracts/inventory.yaml) | OpenAPI 3.1, публічний інтерфейс |
| Сервіс | [`services/inventory/`](../services/inventory/) | FastAPI + власна схема в PostgreSQL + слухач шини |
| Фронтенд-модуль | [`packages/modules/inventory/`](../packages/modules/inventory/) | залишки, прихід, картка деталі, інвентаризація |
| Документація | цей файл | FIFO, резерви, події, межі |

## Що блок віддає

| Метод | Шлях | Право | Що робить |
|---|---|---|---|
| `GET` | `/inventory/stock` | `inventory.read` | залишки: пошук за артикулом, брендом, назвою, коміркою; `low=true` — нижче мінімуму |
| `GET` | `/inventory/stock/{partId}` | `inventory.read` | картка: партії, резерви, рух |
| `PATCH` | `/inventory/stock/{partId}` | `inventory.write` | комірка й мінімальний залишок |
| `POST` | `/inventory/stock/{partId}/count` | `inventory.write` | інвентаризація: фактична кількість |
| `POST` | `/inventory/receipts` | `inventory.write` + `catalog.read` | прихід партії деталі з прайсу |

Права: `inventory.write` — власник і комірник; `inventory.read` — ще й
адміністратор. Механік склад не бачить.

## Залишок — не число в рядку

У базі немає поля «кількість». Усе виводиться з двох таблиць:

```
на складі = Σ lots.qty_left
резерв    = Σ reservations.qty, де active
вільно    = на складі − резерв            може бути відʼємним — видно червоним
вартість  = Σ lots.qty_left × lots.unit_cost
```

Так залишок не може розійтися з партіями, а резерв — з нарядами. Кожна зміна
залишку блокує картку деталі (`SELECT … FOR UPDATE`), тож два одночасні
списання не візьмуть ту саму партію.

## FIFO

Партія — прихід за однією ціною. Списання (наряд закрито, нестача при
інвентаризації) бере з найстаріших партій, собівартість — за їхніми цінами:

```
партії: 10 × 900 ₴ (1 травня), 20 × 1000 ₴ (3 травня)
списати 12 → 10 × 900 + 2 × 1000 = 11 000 ₴; лишилось 18 × 1000 ₴
```

Надлишок при інвентаризації стає новою партією за ціною останнього приходу.

## Резерви

Один резерв на рядок наряду (`line_id`). Нова подія про той самий рядок
перезаписує кількість, а не додає: змінили 3 на 12 — у резерві 12. Події можуть
прийти не в тому порядку — кожна несе час, старіша за збережену ігнорується.
Скасований рядок чи наряд лишає «надгробок» — неактивний резерв з часом, щоб
запізніле `parts.reserved` його не воскресило.

## Що блок слухає

| Подія | Від кого | Що робить |
|---|---|---|
| `part.created`, `part.updated` | `catalog` | заводить або оновлює картку деталі (артикул, бренд, назва, одиниця) |
| `parts.reserved` | `work-orders` | ставить або змінює резерв рядка |
| `parts.released` | `work-orders` | знімає резерв рядка |
| `order.cancelled` | `work-orders` | знімає всі резерви наряду |
| `order.closed` | `work-orders` | списує зарезервоване за FIFO, резерви знімаються |
| `purchase.received` | `procurement` | заводить партії за цінами з накладної; картку деталі — якщо її ще не було |

Слухач — черга `inventory.events`. Підтвердження після коміту; повтор події
безпечний: на рядок наряду може бути лише один рух `issue` (унікальний
частковий індекс), тож двічі не спише. Так само рядок приходу від
`procurement` стає партією один раз — унікальний рух `receipt` з його id.

Якщо деталі не вистачило — списується, скільки є, а в русі нотатка
«Не вистачило X — перевірте залишок»: авто вже поїхало з деталлю, облік хибний.

## Що блок публікує

| Подія | Коли | Хто слухає і навіщо |
|---|---|---|
| `stock.received` | прихід — вручну чи від `procurement`; несе `low` — чи деталь досі нижче мінімуму | `procurement` — закрити потребу; `analytics` |
| `stock.low` | вільне **перетнуло** мінімум донизу (не на кожну подію під ним); несе артикул, назву й одиницю | `procurement` — потреба й чернетка замовлення |
| `stock.issued` | деталь списано в наряд | `finance`, `analytics` — собівартість наряду |
| `stock.discrepancy` | при списанні не вистачило | `notifications` — комірнику |

## Запуск

```bash
docker compose up -d postgres rabbitmq
cd services/inventory
cp .env.example .env        # розкоментуйте RABBITMQ_URL — інакше резервів не буде
uv sync --group dev
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --port 8007
```

## Перевірки

```bash
cd services/inventory
uv run pytest         # 17 тестів
uv run ruff check .
uv run mypy app

cd ../..
pnpm --filter @baymeister/module-inventory typecheck
```

Перевірено наскрізно зі справжнім RabbitMQ: `part.created` заводить картку;
резерв 3 → зміна на 12 дає резерв 12 і рівно один `stock.low`; `order.closed`
списує 12 за 11 000 ₴ (10 × 900 + 2 × 1000).
