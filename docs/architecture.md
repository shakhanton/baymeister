# Архітектура Baymeister

CRM для автосервісу. Сімнадцять вертикальних блоків, кожен із власним
бекенд-сервісом, фронтенд-модулем і контрактом. Одна людина бере один блок і не
чекає на решту. Меню знає про всі блоки одразу — але веде тільки в готові.

**Редакція 1.0** · 18.09.2026 · статус: проєкт рішення

---

## Рішення в трьох реченнях

Фронтенд — **React 19 + TypeScript + Vite** у монорепозиторії, де кожен блок є
окремим пакетом із власним маніфестом. Бекенд — незалежні сервіси на
**Python + FastAPI** за API Gateway, у кожного власна база; спілкування синхронне
через REST-контракти і асинхронне через шину подій.

Пункт меню сірий або клікабельний залежно від одного поля `status` у маніфесті
модуля — інтеграція готового блоку зводиться до зміни цього поля і додавання
маршрутів.

---

## 1. Фронтенд-стек

Вимога: фреймворк, популярний давно, популярний зараз і з активною розробкою на
роки вперед.

**React** — обрано. З 2013 року, найбільша частка ринку, Meta вкладає в нього
власні продукти. Найбільший пул розробників — критично, коли блоки розбирають
різні люди. Найбільша екосистема готових рішень для таблиць, форм і графіків, а
CRM — це саме вони.

**Vue / Angular / Svelte** — не обрано. Vue і Svelte технічно приємніші, але пул
розробників вужчий. Angular стабільний і повний з коробки, проте поріг входу для
студента вищий. Жоден не дає переваги, яка переважила б доступність кадрів.

### Vite, а не Next.js

Next.js популярніший за голий React-SPA, але його головна сила — рендер на
сервері заради SEO. CRM живе за логіном: індексувати нічого. Натомість Next тягне
за собою Node-рантайм, який доведеться деплоїти й моніторити поруч із
мікросервісами. SPA на Vite збирається в статику і роздається з CDN — нуль
серверів на фронті.

| Роль | Вибір |
|---|---|
| Каркас | React 19 + TypeScript + Vite |
| Маршрути | React Router v7 |
| Серверний стан | TanStack Query |
| Клієнтський стан | Zustand |
| UI | Tailwind CSS v4 + shadcn/ui |
| Форми | React Hook Form + Zod |
| Таблиці | TanStack Table |
| Монорепо | pnpm workspaces + Turborepo |
| Тести | Vitest + Testing Library + Playwright |

> **Про shadcn/ui.** Це не бібліотека-залежність, а генератор: компонент
> копіюється у наш код і далі наш. Для проєкту, де дизайн має бути власним і де
> код пишуть різні люди, це важливіше за зручність оновлення — ніхто не
> заблокований чужим релізом.

## 2. Що таке блок

Блок — це **вертикальний зріз**, а не шар. Людина, яка бере «Склад», отримує і
таблиці в базі, і бекенд-сервіс, і екрани, і контракт. Вона не чекає, поки хтось
інший «зробить бекенд для складу».

Один блок = чотири артефакти, усі в одному володінні:

- `services/inventory/` — бекенд-сервіс і його база
- `contracts/inventory.yaml` — OpenAPI-специфікація, публічний інтерфейс блоку
- `packages/modules/inventory/` — фронтенд-модуль: екрани, маршрути, маніфест
- `docs/inventory.md` — що робить блок, які події шле, що ламається без нього

### Структура монорепозиторію

```
baymeister/
├─ apps/
│  └─ shell/                 ← каркас: меню, авторизація, реєстр
├─ packages/
│  ├─ ui/                    дизайн-система, спільна для всіх
│  ├─ module-kit/            типи AppModule, хелпери реєстрації
│  ├─ api-client/            згенеровані з OpenAPI клієнти
│  └─ modules/
│     ├─ customers/          ← блок, одна людина
│     ├─ vehicles/           ← блок, одна людина
│     └─ …
├─ services/
│  ├─ gateway/
│  ├─ identity/
│  └─ …
└─ contracts/
   ├─ customers.yaml
   └─ …
```

> **Чому монорепо, а не Module Federation.** Мікрофронтенди дають справжню
> незалежність деплою, але коштують окремих пайплайнів, версіонування спільних
> залежностей і болючої відладки. Для команди, де блоки беруть студенти, ця ціна
> не окупається. Монорепо з жорсткими межами між пакетами дає ті самі
> організаційні переваги майже задарма. Перейти на Module Federation можна
> пізніше — маніфест модуля спроєктований так, щоб це не ламало каркас.

## 3. Реєстр і сіре меню

Меню, де всі пункти на місці з першого дня, але неготові — сірі. Це не
косметика, а механізм інтеграції: реєстр модулів є єдиним джерелом правди і про
вигляд меню, і про існування маршруту.

Поки `status` не дорівнює `ready`, каркас не реєструє маршрути модуля взагалі —
неготовий блок не може зламати збірку чи навігацію, навіть якщо його код уже в
репозиторії.

### Маніфест модуля

```ts
// packages/modules/work-orders/src/module.ts
import type { AppModule } from '@baymeister/module-kit';

export const workOrdersModule: AppModule = {
  id: 'work-orders',
  title: 'Наряд-замовлення',
  icon: 'clipboard-list',
  status: 'ready',            // 'planned' | 'in-progress' | 'ready'
  nav: { group: 'operations', order: 20 },
  permissions: ['work_orders.read'],
  routes: [
    { path: '/work-orders',     lazy: () => import('./routes/List') },
    { path: '/work-orders/:id', lazy: () => import('./routes/Detail') },
  ],
};
```

### Заглушка для ненаписаного блоку

```ts
export const payrollModule: AppModule = {
  id: 'payroll',
  title: 'Зарплата',
  icon: 'wallet',
  status: 'planned',         // ← єдина відмінність
  nav: { group: 'finance', order: 40 },
  permissions: ['payroll.read'],
  routes: [],                // поки порожньо
};
```

> **Сірий пункт — це не `<a>` з `pointer-events: none`.** Заглушка має бути
> `<span>` з `aria-disabled`: вимкнене посилання все одно потрапляє у фокус з
> клавіатури і читається скрінрідером як робоче.

### Чому не просто фіче-прапорці

Прапорці вмикають готовий код. Тут задача інша: показати пункт меню для коду,
якого ще не існує. Реєстр дозволяє описати весь продукт одразу — виконавець
бачить своє місце в системі до того, як напише перший рядок. Коли блок готовий,
прапорці додаються зверху, на рівні `status: 'ready'` плюс умова.

## 4. Карта сервісів

Фронтенд ніколи не звертається до сервісів напряму. Єдина точка входу —
gateway: він перевіряє токен, маршрутизує і, де треба, склеює відповіді кількох
сервісів в одну.

```
  Shell SPA ──HTTPS──▶ API Gateway ──REST+JWT──┬─▶ identity     (власна БД)
  React, статика                перевірка JWT  ├─▶ customers    (власна БД)
  з CDN                         агрегація      ├─▶ vehicles     (власна БД)
                                               ├─▶ work-orders  (власна БД)
                                               ├─▶ inventory    (власна БД)
                                               └─▶ …            (власна БД)
                                                     │    ▲
                                       order.completed│    │parts.reserved
                                                     ▼    │
                                            ┌─────────────────────┐
                                            │ Шина подій RabbitMQ │
                                            └─────────────────────┘
```

Суцільні стрілки — синхронні запити на читання і команди. Події — асинхронні:
`work-orders` публікує завершення наряду, `finance` і `notifications` реагують
незалежно. Саме це дозволяє блокам не знати один про одного.

продукт: клієнт, авто, запис, наряд, прайс.

> **`work-orders` — це ядро.** Він єдиний залежить від трьох блоків одразу і від
> нього залежить половина решти. Віддавати його найсильнішому виконавцю. Якщо він
> поїде, поїде весь графік.

## 6. Контракти

Блоки пишуть різні люди в різному темпі. Єдине, що тримає це разом — правило:
**контракт пишеться і мерджиться раніше за реалізацію**.

1. Виконавець блоку описує `contracts/<блок>.yaml` — OpenAPI 3.1: ендпоінти,
   схеми, коди помилок.
2. Контракт іде окремим PR і рев'юється. Це єдиний момент, де потрібна увага
   власника проєкту до чужого блоку.
3. CI генерує типізованого клієнта в `packages/api-client` —
   `openapi-typescript` плюс `openapi-fetch`.
4. Далі бекенд і фронтенд блоку пишуться паралельно, навіть різними людьми.
   Фронт працює проти мок-сервера, піднятого з тієї ж специфікації.

> **Правило, яке рятує проєкт.** Зміна контракту, що ламає сумісність — це нова
> версія шляху (`/v2/orders`), а не правка на місці. Блок, що зламав чужий блок
> мовчазною зміною поля, коштує днів відладки.

### Чого блок не робить ніколи

- Не ходить у чужу базу — тільки через API або події.
- Не імпортує код іншого модуля напряму; спільне живе в `packages/ui` і `module-kit`.
- Не додає своїх глобальних стилів — тільки токени дизайн-системи.
- Не змінює файли каркаса, крім одного рядка в реєстрі.

## 7. Дані та події

У кожного сервісу власна схема в PostgreSQL, і ніхто не читає чужу. Це головна
ціна мікросервісів і водночас те, що робить блоки справді незалежними.

### Дублювання — це нормально

`work-orders` зберігає в себе ім'я клієнта і номер авто, хоча володіють ними
`customers` і `vehicles`. Інакше кожен список нарядів перетворюється на віяло
запитів. Копія оновлюється подією `customer.updated`, а не запитом на льоту.

### Події, з яких усе починається

| Подія | Публікує | Хто слухає і що робить |
|---|---|---|
| `order.created` | work-orders | scheduling резервує пост; notifications шле SMS |
| `order.completed` | work-orders | finance створює рахунок; payroll нараховує; analytics оновлює read-модель |
| `parts.reserved` | work-orders | inventory списує з вільного залишку |
| `stock.low` | inventory | procurement формує чернетку замовлення |
| `payment.received` | finance | work-orders закриває наряд; documents готує акт |

Кожен слухач обробляє подію ідемпотентно — повторна доставка не повинна
нараховувати зарплату двічі.

## 8. Бекенд

Очевидний аргумент за Node — «одна мова з обох боків, спільні типи» — тут майже
не працює. Ми вибрали contract-first: типізований TypeScript-клієнт генерується з
OpenAPI **незалежно від мови бекенда**. Фронт отримує однакові типи і від
FastAPI, і від NestJS. Головна вигода від симетрії вже забезпечена іншим
механізмом.

Тому рішення визначають люди, а не мова. Пул виконавців — студенти, у яких Python
зазвичай сильніший за Node.

| Роль | Вибір |
|---|---|
| Мова | Python 3.12+ |
| Фреймворк | FastAPI |
| Валідація | Pydantic v2 |
| База | PostgreSQL, схема на сервіс |
| ORM | SQLAlchemy 2.0 + Alembic |
| Шина | RabbitMQ + aio-pika |
| Фонові задачі | arq |
| Залежності | uv |
| Якість | Ruff + mypy + pytest |
| Файли | S3-сумісне сховище |
| Локально | Docker Compose |

### Чому не Django

Сила Django — моноліт з ORM і адмінкою. Схема «база на сервіс» ріже цю силу
навпіл: адмінка не бачить чужих даних, а сімнадцять Django-проєктів дають багато
церемонії на порожньому місці.

Виняток один: якщо проєкт усе ж піде в бік модульного моноліту (див. розділ 11),
Django з `django-ninja` стає сильним варіантом — адмінка з коробки закриває
більшу частину довідників і CRUD-екранів Фази 1 без жодного рядка фронтенду.

> **Одна мова на всьому бекенді.** Contract-first технічно дозволяє писати окремі
> сервіси іншою мовою — межа проходить по OpenAPI, а не по рантайму.
> Організаційно це погана ідея: подвоєний CI, два набори шаблонів і два способи
> робити те саме.

## 9. Фази

Порядок продиктований залежностями, а не важливістю.

**Фаза 0 — каркас.** Shell, дизайн-система, реєстр із усіма 17 блоками у стані
`planned`, авторизація, gateway. На виході — застосунок, де працює вхід і видно
повне меню, майже все сіре.

**Фаза 1 — мінімальний робочий цикл.** `customers`, `vehicles`, `catalog`,
`scheduling`, `work-orders`. Після неї автосервіс може реально приймати машину,
вести наряд і закрити його. П'ять блоків — п'ять виконавців паралельно.

**Фаза 2 — гроші й склад.** `inventory`, `procurement`, `finance`,
`inspections`, `files`. Тут з'являється більшість подій і перша реальна перевірка
асинхронної частини.

**Фаза 3 — надбудова.** `payroll`, `analytics`, `documents`, `notifications`,
`integrations`. Усі п'ять переважно читають чужі події й майже нічим не
володіють — тому й останні.

## 10. Порядок робіт по каркасу

1. **Монорепо.** pnpm workspaces, Turborepo, TypeScript у strict, ESLint з
   правилом, що забороняє імпорт між модулями.
2. **Дизайн-система.** Токени, типографіка, Tailwind-конфіг, базовий набір
   shadcn/ui.
3. **`module-kit`.** Тип `AppModule`, хелпери реєстрації, компонент `NavItem`.
   Це контракт між каркасом і всіма майбутніми блоками.
4. **Каркас застосунку.** Бічне меню з груп, хедер, хлібні крихти, сторінка 404,
   стани завантаження й помилки.
5. **Реєстр із 17 заглушок.** Усі блоки з таблиці, усі `status: 'planned'`.
6. **Identity + gateway.** Вхід, ролі, захищені маршрути. Перший наскрізний зріз.
7. **Демо-блок.** Довести `customers` до `status: 'ready'`. Він стане зразком,
   який видається виконавцям замість документації.

> **Чому демо-блок важливіший за інструкцію.** Виконавець, що бачить готовий
> `customers` з маніфестом, контрактом, тестами і екранами, скопіює структуру за
> годину. Той самий виконавець, що отримав текстовий опис, зробить по-своєму — і
> рев'юватиметься не логіка, а розкладка файлів.

## 11. Ризики

### Мікросервіси на старті — дорого

Сімнадцять сервісів для команди без досвіду розподілених систем — це реальний
ризик. Розподілені транзакції, ідемпотентність, відладка через кілька сервісів:
усе це складніше за моноліт і не дає жодної переваги, поки навантаження мале.

Вимога «блоки можуть писати різні люди» вирішується і модульним монолітом: ті
самі межі, ті самі контракти, один процес і одна база зі схемами. Якщо мета —
паралельна робота людей, а не масштабування, модульний моноліт дає те саме

### Фронтенд-каркас стає вузьким місцем

Усі 17 блоків проходять через один реєстр і одну дизайн-систему. Якщо власник не
встигає рев'ювати, черга росте. Пом'якшення: жорсткий `module-kit` і демо-блок як
зразок.

### Контракти писатимуть погано

Найімовірніша точка відмови. OpenAPI без досвіду виходить неточним, і
розбіжність спливає на інтеграції. Пом'якшення: рев'ю контракту як окремий PR до
початку реалізації, плюс наскрізні тести, що ганяють реальні запити через
gateway.

### Обсяг

Сімнадцять блоків силами виконавців, що змінюються щосеместру — це план на кілька
років, не на один. Фаза 1 з п'яти блоків реалістична; далі темп залежить від
того, скільки людей затримається довше за один блок.
