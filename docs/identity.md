# Блок `identity`

Співробітники автосервісу, їхні ролі й права, вхід і токени доступу.

## Чотири артефакти блоку

| Артефакт | Де лежить | Що це |
|---|---|---|
| Контракт | [`contracts/identity.yaml`](../contracts/identity.yaml) | OpenAPI 3.1, публічний інтерфейс |
| Сервіс | [`services/identity/`](../services/identity/) | FastAPI + власна схема в PostgreSQL |
| Фронтенд-модуль | [`packages/modules/identity/`](../packages/modules/identity/) | екрани співробітників, маніфест, хуки |
| Документація | цей файл | межі блоку, токени, події |

Екран входу й сесія — не частина модуля, а каркаса (`apps/shell/src/auth/`):
вони потрібні ще до того, як відомо, які модулі користувачу доступні.

## Що блок віддає

| Метод | Шлях | Право | Що робить |
|---|---|---|---|
| `POST` | `/identity/auth/login` | — | email + пароль → токен і поточний користувач |
| `GET` | `/identity/.well-known/jwks.json` | — | публічний ключ для перевірки токенів |
| `GET` | `/identity/me` | будь-який вхід | хто я і які мої права |
| `GET` | `/identity/roles` | `identity.read` | каталог ролей |
| `GET` | `/identity/users` | `identity.read` | список із пошуком, пагінацією, вимкненими |
| `POST` | `/identity/users` | `identity.write` | додати співробітника |
| `GET` | `/identity/users/{id}` | `identity.read` | один співробітник |
| `PATCH` | `/identity/users/{id}` | `identity.write` | змінити імʼя, email, роль, пароль |
| `POST` | `/identity/users/{id}/deactivate` | `identity.write` | заборонити вхід |
| `POST` | `/identity/users/{id}/activate` | `identity.write` | повернути доступ |

## Як працює вхід

```
 Shell ──POST /api/identity/auth/login──▶ Gateway ──▶ identity
       ◀──────────── access_token (JWT, RS256) ─────────────┘

 Shell ──GET /api/customers + Bearer──▶ Gateway ──перевірка підпису за JWKS──┐
                                          │                                  │
                                          └──X-User-Id / Role / Permissions──▶ customers
```

1. identity підписує токен **приватним** RSA-ключем. У токені — `sub`, роль і
   список прав (`perms`), `exp` — 8 годин, одна зміна.
2. gateway бере **публічний** ключ з JWKS і перевіряє кожен запит локально, без
   звернення до identity. Ключі кешуються: якщо identity впав, ті, хто вже
   увійшов, працюють далі.
3. Сервіси токен не розбирають. Вони читають `X-User-*`, які виставив gateway,
   і самі вирішують, яке право потрібне ендпоінту. Зразок —
   `services/identity/app/api/auth.py`, копіюється в кожен блок як є.

Спільного секрету між сервісами немає. Зламаний gateway не може випустити
токен — лише пропустити чужий запит.

## Ролі

Ролі — код (`services/identity/app/roles.py`), не таблиця. Набір посад
стабільний, а права мусять змінюватись разом із кодом, який їх перевіряє.

| Роль | Хто це | Права |
|---|---|---|
| `owner` | власник | `*` — усе |
| `manager` | адміністратор-приймальник | клієнти, авто, запис, наряди, огляди, документи — читання й зміни; прайс, склад, каса, звіти — читання |
| `mechanic` | механік | огляди — зміни; наряди, авто, клієнти, запис, прайс — читання |
| `cashier` | касир | каса — зміни; клієнти, наряди, документи — читання |
| `storekeeper` | комірник | склад і закупівлі — зміни; прайс, наряди — читання |

Право — `<блок>.read` або `<блок>.write`; дефіс в id блоку стає
підкресленням: `work_orders.read`. Новий блок, що перевіряє нове право, додає
його відповідним ролям у тому ж PR.

## Що блок публікує

| Подія | Коли | Хто слухає і навіщо |
|---|---|---|
| `user.created` | додано співробітника | `payroll` — заводить картку |
| `user.updated` | змінено імʼя або роль | `scheduling`, `payroll`, `analytics` — оновлюють власну копію |
| `user.deactivated` | вимкнено | `scheduling` — прибирає механіка з планувальника |
| `user.activated` | увімкнено знову | `scheduling` — повертає |

## Межі

**Вимкнення мʼяке.** Співробітник не може увійти, але лишається доступним за
ідентифікатором — наряди й табель на нього посилаються.

**Останній власник захищений.** Не можна вимкнути, понизити в ролі чи вимкнути
самого себе, якщо після цього в системі не лишиться жодного активного
власника. Інакше системою ніхто не керує, і відновлення — тільки через базу.

**Зміна ролі — з наступного входу.** Права лежать у токені, щоб gateway не
питав identity на кожен запит. Ціна: виданий токен живе до свого `exp`.
`/identity/me` повертає актуальні права, тому меню після перезавантаження
сторінки вже правильне, а бекенд доганяє з наступним входом.

**Помилка входу не підказує.** «Невірний email або пароль» — і для чужого
email, і для неправильного пароля, і для вимкненого облікового запису. Пароль
перевіряється навіть коли email не знайдено, щоб не видавати це часом відповіді.

**Email — у нижньому регістрі.** `Oleh@` і `oleh@` — одна людина.

## Ключ підпису

Без `JWT_PRIVATE_KEY` / `JWT_PRIVATE_KEY_FILE` сервіс генерує тимчасовий ключ
при старті. Локально це зручно; після перезапуску всі видані токени стають
недійсними — каркас сам поверне на екран входу. У проді ключ обовʼязковий:

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out jwt.pem
```

`kid` — хеш публічного ключа, тож ротація — це просто новий файл. gateway,
побачивши невідомий `kid`, перечитає JWKS (не частіше ніж раз на 5 секунд).

## Запуск

```bash
docker compose up -d postgres
cd services/identity
cp .env.example .env
uv sync --group dev
uv run alembic upgrade head
uv run python -m app.bootstrap      # перший власник з BOOTSTRAP_OWNER_*
uv run uvicorn app.main:app --reload --port 8002
```

`app.bootstrap` створює власника, тільки якщо база порожня, — його можна
безпечно лишити в скрипті деплою після міграцій.

## Перевірки

cd services/identity

## Що лишилось зробити

- Refresh-токени. Зараз після 8 годин — повторний вхід.
- Відкликання токена до `exp` (вимкнений співробітник працює до кінця зміни).
- Скидання пароля через email — чекає на блок `notifications`.
- Обмеження спроб входу — разом із rate limit у gateway.
